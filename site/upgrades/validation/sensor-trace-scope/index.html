    Sensor trace scope implementation validation

    Date: 24 October 2026 (Australia/Sydney). Revision: working tree based on 99dc1448 on meshcore/sensor.

    Implemented behaviour

    • Replies capture the selected transport key, channel and path-hash width when accepted. Ordinary multipart replies, trace success/failure reports, delayed fallback, busy notices and allocation/queue retries retain their own context.
    • Recognised scope is mirrored; explicitly unscoped floods remain unscoped; unresolved/direct requests use the usable default, otherwise unscoped. Pending replies retain their captured selection across default changes or region removal. Transport codes are computed from each new reply payload.
    • Candidate matching and the four-entry, fifteen-minute RAM history are scoped by the complete resolved transport key. Unresolved scopes do not reuse history; within a transaction their copies must match both transport codes and route class as well as command ciphertext. Short-code ambiguity remains possible, so these are conservative hints rather than proven node identities.
    • Region resolution uses the packet being observed and performs no persistent writes. Multiple configured keys matching one short code are treated as unresolved. Names/region IDs are not history identities.
    • The production and native runtimes instantiate the same SensorScopeBinding. Generic capture/selection/send helpers are shared with the upstream sensor; bot-specific context stays in the BME680 application. The trace packet format, two-attempt limit, timeout policy and conservative failure wording are retained.

    The recorded check summaries contain the test suite and firmware results.

    The regular checks use:

    pio test -e native -e native_sensor -e native_kiss_modem
bash bin/check-sensor-boundaries.sh

    The sensor sanitizer checks use the existing native_sensor_asan source and flags with ASAN_OPTIONS=detect_leaks=0, as documented by the project. The host compiler's ASan linker script pointed at a missing system library, so the first attempt could not link. Validation downloaded and extracted the matching Fedora libasan-16.2.1-2.fc44.x86_64 RPM under /tmp, without installing a system package. A temporary copy of the project configuration adds only the local library search path/rpath and an isolated build directory:

    ASAN_OPTIONS=detect_leaks=0 pio test \
  -c /tmp/meshcore-scope-asan.ini -e native_sensor_asan

    The temporary config uses -L/tmp/meshcore-scope-asan-runtime/usr/lib64, -Wl,-rpath,/tmp/meshcore-scope-asan-runtime/usr/lib64, and build_dir = /tmp/meshcore-scope-asan-build. No sanitizer was disabled beyond existing leak detection policy. The temporary sanitizer build directory is isolated so local configuration changes do not invalidate firmware outputs.

    New regression coverage includes five focused Dispatcher lifecycle tests, eighteen scope integration/binding tests, four scope/history candidate tests and four scoped network-medium cases. Existing coverage continues to exercise pool reuse, cancellation, expiry, uncertain sends, temporary radio changes, late-result fallback, ambiguity display and physical-path geometry.

    Physical acceptance

    Not run. No device was flashed. Automated packet-medium tests cannot verify physical delivery, actual RF contention, RTT timing or directional SNR order.

    The implementation plan remains the physical checklist: scoped delivery through relays rejecting unscoped floods; both channels and hash widths; delayed multipart and default scope changes; slower radio and contention timing; retry/fallback without contradictory reports; outward-hop SNR order; telemetry/admin persistence and UF2/OTA update smoke tests. Record physical results independently before marking hardware acceptance complete.
