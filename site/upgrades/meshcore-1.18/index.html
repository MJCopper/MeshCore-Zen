    MeshCore 1.18 integration and acceptance record

    Release baseline: 81dbae592ffad40b4212bc0b37e82b38da08f4bc, shared by official companion-v1.18.0, repeater-v1.18.0 and room-server-v1.18.0 tags. Validation date: 20 October 2026 (Australia/Sydney).

    Status: software integration and automated validation recorded below. Hardware acceptance remains pending. This record does not claim every physical feature has been tested or authorize a production release.

    Recovery and branch isolation

    The local meshcore/main branch was fast-forwarded from d9296435 to the release. The three product branches independently merge that baseline without rebasing or force-pushing. Backup refs retain each original product:

    Branch Original commit Backup ref
    meshcore/main d9296435 backup/pre-1.18-meshcore-main
    zen/main e35bceea backup/pre-1.18-zen
    meshcore/sensor 90f9cbcb backup/pre-1.18-sensor
    meshcore/archiver 981c5872 backup/pre-1.18-archiver

    Device rollback requires a saved settings backup and matching previous firmware. Do not assume newer preference files can be read by older firmware. The archive history is intentionally volatile and cannot survive an upgrade/reboot.

    Integration decisions

    • Zen keeps its presentation, message histories, child-mode permissions, notifications, power policies and UI callbacks. The 1.18 listener extension API coexists with this context-rich UI binding. The binding is explicitly retained in the boot composition; replacing it with an unregistered listener would silently disable standalone features.
    • Zen incorporates protocol version 14, local and permitted remote CLI, unsolicited binary responses (including telemetry push), multi-byte raw paths, updated GPS diagnostics and board lifecycle/dynamic preferences. Remote CLI cannot execute while Child Mode is restricted. CLI timezone changes select Zen's fixed-offset mode so clock, quiet time and pet schedules agree.
    • Zen retains repeater Yield x2 and uses the new configurable transmit-delay factors. The new baseline preference fields participate in save suppression; dynamic preference dirty state also forces a baseline save.
    • Sensor retains its application policy hooks, guest telemetry, admin ACL persistence, leaf policy, environmental transformations and public bot. The 1.18 sensor runtime supplies subscriptions, region loading and board hooks. Subscription thresholds are bounds-checked before state mutation; humidity keeps its one-byte, half-percent encoding. Push telemetry reserves its extra timestamp bytes. Custom serial commands use the updated runtime signature.
    • Archiver retains the Public decoder, RAM ring, room snapshot boundaries, hop-dependent history limit, read-only policy and ACK-driven synchronization. Production snapshot selection was extracted into a directly tested policy; normal room-server builds remain free of archive policy.
    • Baseline sources remain exactly upstream in Zen's protected paths. Reviewed overlay counterpart hashes and the sensor boundary pin now reference 1.18. PlatformIO environments, firmware filenames and CI branch tests are retained.

    End-to-end release gate (pending)

    Use OLED and E-ink Zen devices, the BME680 sensor, the archive, an official 1.18 companion and a 1.17.1 peer. Exercise direct, one-hop and two-plus-hop routes:

    • Poll and subscribe from a companion while sensor bot/trace traffic runs; receive pushed telemetry, unsubscribe and verify expiry.
    • Synchronize archive snapshots from Zen and official companions, including messages arriving during synchronization and all access roles.
    • Verify old saved identities, contacts, channels, ACL, Zen preferences and pet records; export and restore settings before/after flashing.
    • Introduce radio congestion, lost ACKs, disconnect/reconnect, reboot and low power; verify recovery and bounded memory/queues.
    • Run at least 24 hours across a quiet-time boundary and archive wraparound; retain logs, memory readings, traffic observations and device identifiers.

    No identifiable supported USB firmware devices were available; the host exposed only generic ttyS entries. Physical display, RF, GPS, sensor, battery, OTA, mixed-firmware interoperability and soak tests are therefore PENDING. Promote/release only after recording those results.

    Artifact verification

    Artifact checksums and UF2 block counts were recorded after validating UF2 magic words, family ID, block sequence/count, payload sizes and embedded firmware version. Sensor/archive DFU ZIP manifests and ZIP integrity were checked. Paths under /tmp identify the isolated local worktrees used for those branch builds. These checks do not replace flashing.

    The branch validation evidence is retained as test results, firmware builds and documentation build.
